# E1 报告 — 离线判官：历史先例能否预测「你会怎么回答」

> 2026-10-27 · 模型 v4.1flash（workers 网关，thinking 关闭）· 计划见 `EXPERIMENT-PLAN.md`
> 数据与 journal：`tmp/cockpit-judge/`（gitignore）；所有指标由 `analyze.py` 从 journal 离线计算。

## 1. 结论
- **会话提问不应自动执行。** 任何类别、任何置信度都达不到 90% 精度；准确率 A2 20.7%、A3 24.2%，低于「永远猜最常见答案」（A0 26.0%）。
- **历史先例有一点作用但不显著**：A3 − A2 = +3.5 pp，95% 区间 [−1.3, +8.0]。
- **「阻塞修好再重派」不能作为第一个自动类别**（至少不能靠失败原因 + 提交标题）：E1b AUC 0.557；挂起精度约 0.60–0.65 ≈ 基准失败率 0.58。
- 计划 §8 过关线：**全部未过**。

## 2. 方法
| 步骤 | 内容 |
|---|---|
| 数据 | 近 30 天 1181 对「助手提问 → 用户回答」（仅人类会话） |
| 标注 | LLM 按回答方式标 6 类：ACCEPT / ACCEPT_WITH_CHANGES / ALTERNATIVE / INVESTIGATE / DISCUSS / OTHER（输入：提问尾 900 字 + 回答 400 字） |
| 标注核对 | 另一个模型独立读 60 条随机样本：完全一致 37/60（62%），粗分（同意/否决/要更多/其他）42/60（70%）。不是真值，只说明标签噪声大 |
| 评估窗口 | 按时间最近 400 对；更早 781 对只作历史（先例严格取更早的） |
| A0 | 先验：最常见答案 ACCEPT_WITH_CHANGES |
| A1 | 字符二元 TF-IDF，更早的 8 条先例加权投票 |
| A2 | LLM 判官，只看提问 |
| A3 | LLM 判官，提问 + 6 条更早相似先例（带标签与回答摘录） |
| E1b | 同签名已连续失败 ≥2 次的 173 次尝试；判官看前几次失败原因 + 期间 develop 提交标题，预测这次能否落地 |

## 4. 结果
评估 400 对的标签分布：ACCEPT_WITH_CHANGES 104 · DISCUSS 72 · ACCEPT 70 · INVESTIGATE 63 · OTHER 52 · ALTERNATIVE 39

| 臂 | 准确率 | 90% 精度下覆盖 | ECE |
|---|---|---|---|
| A0 先验 | 0.260 | — | — |
| A1 检索投票 | 0.278 | 0 | — |
| A2 判官 | 0.207 | 0 | 0.309 |
| A3 判官 + 先例 | 0.242 | 0 | 0.267 |

- **按提问类型**（A3 准确率）：go/no-go 0.17（n70）· 记成任务 0.30（n90）· 继续盯/收手 0.36（n22）· 二选一 0.17（n81）· 设计裁定 0.41（n17）· 其它 0.24（n120）。所有类型在 90% 精度下的覆盖均为 0。
- **系统性高估「直接同意」**：A3 判 ACCEPT 185 次、A2 255 次，真实 70 次。A3 置信度最高的 5/10/20/40 条 ACCEPT 精度 0.60/0.50/0.40/0.30。
- **校准差**：A3 自报 0.6–0.8 那档实际准确率 0.245；0.8 以上只有 4 条。
- **高置信度误判示例**（A3）：
  - 0.82 判 ACCEPT，实为 DISCUSS：助手问「要不要实测切换会话的请求次数」，用户转而指出重复打开会话会反复请求 LLM、浪费。
  - 0.82 判 ALTERNATIVE，实为 INVESTIGATE：助手给出移动端三个方案，用户提出第四种（去掉下拉文本、腾空间给迷你甘特图）并要求「检查、分析和讨论」。
  - 0.78 判 ACCEPT，实为 DISCUSS：助手问「要我现在按顺序执行这批任务吗」，用户追问继承/多态、可复用性与重复代码。

## 6. 局限
- 标签噪声大（模型间一致 62%），这会压低所有臂，但解释不了判官低于先验：判官的问题是偏向 ACCEPT、几乎不判 OTHER/INVESTIGATE。
- 6 类标签是粗近似：很多回答同时做决定又加条件或转向。
- 只测了最便宜的 v4.1flash 和提问尾 900 字；更强模型或完整上下文未测。
- E1b 的落地与否还受 develop 红集、并发负载影响，提交标题几乎不含这些信息。

## 7. 建议
- **(a) 会话提问：只做建议，不自动执行。** 默认选项优先用助手自己的推荐（source=assistant）；判官只在助手没给推荐时补一条 source=judge 的建议，不进入委托阶梯的自动档。投入应放在让用户更快看懂问题（情境、选项说明、证据）。
- **(b) 救援类的第一个自动候选需要机械信号**：阻塞项任务已落地、develop 上对应签名的红已消失（baseline-red 读数）。建议由 quay-fleet 基于机械读数给出「可重派」判定，LLM 只解释原因；在此之前救援类保持「建议 + 确认」。

## 9. 事后复算：时间切片——输入是否随时间收敛、判官是否跟着变好（2026-10-28）

**猜想（人提出）**：早期没有 Claude Code UI / 驾驶舱提供推荐与选项，人更多手工输入、变化更大；后来有推荐与具体选项后，输入分布可能收敛，判官任务随之变简单。

**方法**：把 400 条 eval 按 `at` 排序，切早/晚两半（各 200）与四等分；对每段算 clean 率（ACCEPT + ACCEPT_WITH_CHANGES 占比）、A0 基线准确率、A2/A3 准确率（预测取 `argmax(dist)`）。

**结果**：

| 指标 | 早半 | 晚半 | Δ |
|---|---|---|---|
| A0（猜最常见） | 21.5% | 30.5% | +9.0% |
| A2（只看提问） | 21.0% | 20.5% | −0.5% |
| A3（提问+先例） | 23.0% | 25.5% | +2.5% |

四等分（clean 率 / A3 准确率）：Q1 37% / 22.0% → Q2 46% / 24.0% → Q3 41% / 25.0% → Q4 50% / 26.0%。

**解读**：
- **猜想前半成立**：输入分布确实在轻微收敛——clean 率 37%→50%，A0 基线 21.5%→30.5%（任务变简单约 9pp）。
- **猜想后半不成立**：判官没跟着变好——A2 平、A3 只 +2.5pp，且晚半的 A3（25.5%）**仍低于**晚半的 A0（30.5%）。判官的主要错误是偏置（系统性高估 ACCEPT：判 185 次 vs 真实 70 次，而真实众数是 ACCEPT_WITH_CHANGES=104），不是方差——数据越向 ACCEPT_WITH_CHANGES 集中，A0 越受益，判官越吃不到。

**局限**：本数据集是驾驶舱上线**之前**的（人手工输入）。「驾驶舱提供具体选项 + 一键确认之后，输入是否真收敛到选项集」需 post-cockpit 的选择数据验证——对应 fleet 侧「驾驶舱选项选择观测」任务（待立/已立）。
