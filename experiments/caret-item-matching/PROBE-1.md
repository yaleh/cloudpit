# 探针 1：网关、延迟与停顿策略（2026-10-25）

目的：在正式做 393 回合的回放之前，先回答三个问题：

1. workers 网关对“草稿 + 候选段落 → top-3”这个 prompt 的实际延迟和费用；
2. LLM 的 top-1/top-3 相对 lexical 基线有没有可辨认的提升；
3. 在实测延迟下，“按已停顿多久估计还会停多久”的触发策略长什么样。

## 1. 设置

- 样本：`PROBE-SET.json`，16 个“引用 + 意见”回合（8 个来源 ≤3 条消息，8 个更远）。
- 每个回合 3 个候选池：
  - `oracle-neighbors`：源消息 ±1（完美视口，truth 必在池内，capped 32 段）；
  - `naive-12`：最近 12 条消息，lexical top-20（无视口信号）；
  - `tight-12`：最近 12 条消息，lexical top-12（成本更低的预筛）。
- 模型：`v4.1flash`，`thinking: disabled`，temperature 0，max_tokens 200。
- 调用：48 次（16×3），并发 4，重试 2；0 失败，0 JSON 解析失败。
- 隐私：走 workers 网关（用户选择 1）。

## 2. 延迟（这是本轮最重要的读数）

| 读数 | p50 | p95 | max |
|---|---:|---:|---:|
| 完整响应 | **799 ms** | **1,151 ms** | 1,202 ms |
| TTFB（8 次流式） | 557 ms | 966 ms | — |

- **p95 <800ms 对完整响应不成立**。即使 14 token 的 hello-world 调用也要 ~1.0s；
  延迟由网关/模型主导，不是 prompt 长度。
- TTFB 比完整响应早约 250–350ms，但结构化 JSON 需要完整响应才能解析；
  流式对 v1 的价值有限。
- 两次运行的结果有差异（oracle top-3 50% → 43.8%），temperature 0 在这个网关上不是确定性的；
  正式实验每个样本要跑 2–3 次取多数或平均。

## 3. 费用

| 池 | 平均 input tokens（含 cache read） | 其中 cache read | 平均 output | 单次费用上界* |
|---|---:|---:|---:|---:|
| oracle-neighbors | 1,297 | 1,112 | 40 | $0.0015 ≈ ¥0.011 |
| naive-12 | 1,358 | 1,160 | 44 | $0.0016 ≈ ¥0.011 |
| tight-12 | **927** | 736 | 41 | **$0.0011 ≈ ¥0.008** |

*按 $1/M input、$5/M output 估算，所有 input 都按全价算；cache read 通常更便宜，所以是上界。

- 网关的 prompt cache 是工作的：~1k tokens 走 cache read。
- `tight-12` 把单次压到 ¥0.008，进 ¥0.01 预算；`oracle`/`naive` 需要再预筛或接受 ¥0.011。
- 430 个“引用 + 意见”回合 / 21 天 ≈20/天；按 50–100 次调用/天，¥0.4–0.8/天。

## 4. 质量（16 回合，样本太小，只作可行性）

| 池 | top-1 | top-3 | lexical top-3 |
|---|---:|---:|---:|
| oracle-neighbors | 31.2% | 43.8% | 43.8% |
| naive-12 | 0.0% | 37.5% | 25.0% |
| tight-12 | 12.5% | 25.0% | 25.0% |

- oracle 池上 LLM 没有超过 lexical（都 43.8%）；naive 池 +12.5 点；tight 池持平。
- n=16/池，置信区间约 ±24 点；**这不能作为 LLM 有效或无效的判决**，只能说明协议跑通了。
- 失败样本多是“选对了消息、选错同消息里的段落”（如 T01：truth 7:1，picks 6:3/8:3），
  说明段落切分和 ground truth 的粒度也会影响读数。

## 5. 停顿策略：用已停时长估计剩余停时

没有真实击键间隔数据。下面用参数先验（65% 中位 0.12s / 25% 0.45s / 10% 2.50s 的
log-normal 混合）评估策略；拿到真实 keystroke 间隔后直接替换分布即可重跑
`pause-policy.py`。

设：在 t0 时发起调用，延迟 L=1.15s（实测 p95）；用户仍在停顿时才显示（T > t0+L）。

| t0 | 发起率 | 显示/发起 | 浪费/发起 | 长停顿捕获 | E[剩余停顿 \| T>t0] |
|---:|---:|---:|---:|---:|---:|
| 0.2s | 41.8% | 21.0% | 79.0% | 100% | 1.19s |
| 0.3s | 30.0% | 27.5% | 72.5% | 100% | 1.54s |
| **0.5s** | 20.6% | 35.9% | **64.1%** | 100% | **1.99s** |
| **0.7s** | 15.6% | 43.1% | 56.9% | 100% | **2.40s** |
| 0.9s | 12.5% | 49.3% | 50.7% | 100% | 2.77s |
| 1.2s | 9.7% | 56.4% | 43.6% | 85.3% | 3.22s |
| 1.5s | 8.0% | 61.2% | 38.8% | 70.5% | 3.57s |
| 2.0s | 6.3% | 66.0% | 34.0% | 55.3% | 3.98s |

读法：

- **在 t0=0.5–0.7s 发起是理性的**：E[剩余停顿] 1.99–2.40s 大于实测 L=1.15s；
  代价是 57–64% 的调用在用户恢复输入后才回来。
- 想更低浪费就等到 1.2–1.5s，但会漏掉 15–30% 的长停顿，且建议来得更晚。
- “浪费”的调用不一定真浪费：结果按 `(draft, 候选集)` 缓存，用户下一次停顿时可直接显示。
  真正的浪费率只能在 shadow 阶段测。
- 建议的触发条件（在 t0 之外）：
  - 草稿在**子句边界**（句号/问号/换行）→ t0 取 0.4–0.6s；
  - 草稿在**词中**（ASCII alnum 结尾）→ t0 取 0.9–1.2s；
  - 刚发生滚动（500ms 内）→ 视为阅读停顿，t0 取 0.4–0.6s；
  - IME composition、命令/mention 浮层、有选区 → 不触发；
  - 草稿 <8 字 → 不触发；
  - lexical 预筛 <2 个候选 → 不触发。
- 两段式：t=250ms 先跑 lexical（免费），t=t0 再决定是否调用网关；
  如果 lexical 的唯一候选分数明显领先，可以直接显示，不必调模型（需单独校准）。

## 6. 对实验方案的影响

1. **p95<800ms 的门要改**：完整响应改为 **p95 <1.3s**，并在 UI 上允许“建议晚到”；
   或者接受 TTFB ~0.6s 先显示一个“正在找引用”的占位，再替换为结果。
2. **成本门用 tight-12 的读数**（¥0.008/次）作为达标配置；oracle/naive 只用于质量对照。
3. **触发阈值按上表定**：默认 t0=0.6s，按草稿边界/滚动状态调整；结果缓存复用。
4. **正式回放要重复**：temperature 0 不确定，每个样本 2–3 次，报告多数/平均。
5. **样本量**：16 回合只够跑通协议；正式实验至少 60 回合（30 near / 30 far），
   每个池 2 次重复，才能把 ±24 点压到 ±12 点以内。

## 7. 限制

- 先验分布是假设，不是本机真实击键间隔；策略表的绝对值不可引用，只能读趋势。
- 16 回合、一个用户、一个项目；质量数字不作判决。
- 网关费用按 $1/$5 假设；实际价格以网关账单为准。
- 段落切分与 ground truth 粒度会影响 top-3；正式实验要人工复核一部分 miss。
- 流式只测了 8 次，TTFB p95 不稳定。
