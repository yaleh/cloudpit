# 探针 2：补多长，以及“选中即生成建议”的现状（2026-10-25）

两个问题：

1. LLM 补全应该补一句还是补全文？成本差多少？
2. 在现有“选中文本 → 原文 quote chip”的基础上，再生成若干输入建议——现在离这个目标有多远？

## 1. 现状检查：selection focus 已经存在，但不是自动的

- 后端 prompt 已经支持 `focus`：`reply-suggestions-prompts.ts` 的
  `buildUserPrompt` 会加一段「用户选中了消息里的这一段，想回应它」。
- 前端 `useReplySuggestions` 把 `quotedSelection ?? quoteAnchor` 作为 `focus` 传进 controller。
- 但 controller 的首次 draw 只按 `(sessionId, lastAssistantMessageId)` 缓存和触发；
  `focus` 只在**用户按「建议」按钮重抽**时进入请求体（`redraw`，`replySuggestionsController.ts:496`）。
- chip 合并顺序是 **quoted > model > habit**；model/habit chip 只在输入框为空时显示
  （`draftChipsAllowed = conditionsHold && input === ''`），quote chip 在输入框有文字时仍显示。

结论：**“选中 → 原文 chip”已有；“选中 → 自动生成若干建议”缺的是触发与缓存键，不是模型能力。**
扩展主要是前端：

- 选中结束（mouseup/touchend，150ms 去抖）后，用 `focus` 发一次 draw；
- quote chip 立即显示，生成 chip 到达后追加（不阻塞 quote chip）；
- 缓存键改成 `(sessionId, messageId, focusHash)`；
- 用户点了 quote chip 或开始打字 → 取消/隐藏生成 chip。

## 2. 真实使用记录：用户选多长的 chip？

来自 `~/.cloudcli/reply-suggestions-usage.jsonl`（2026-10-24 至 10-25，71 个 draw）：

| 读数 | 值 |
|---|---:|
| 唯一 draw | 71 |
| 至少点选一次的 draw | 20（28.2%） |
| 有 sent 的 draw | 15（21.1%） |
| picked 事件 | 43 |
| 点选 index 0 / 1 / 2 | **35 / 8 / 0** |
| 所有 chip 长度 p50 / p90 / max | 21 / 54 / 114 |
| index 0 长度 p50 / max | 37 / 114 |
| index 1 长度 p50 / max | 21 / 89 |
| index 2 长度 p50 / max | 17 / 46 |
| 被点选 chip 长度 p50 / max | **39 / 114** |

读法：

- 用户**几乎只点第一条**（81%），而第一条是「回答所有待答点、采纳建议」的较完整短回复；
  第 2、3 条更短，主要作为备选。
- 但“较完整”仍然只是 **39 字符中位、114 字符上限**，不是整条消息。
- 现有产品（≤120 字符、3 条、第 1 条最完整）已经是“补一句到一小段”，不是“补全文”。
- `reply-suggestions-bench replay` 自己报的是 pickedRate 7%（5/71）、0 个可比较的改后发送；
  那是它按 `served` 过滤后的口径。两种口径都列出来，别只看一个。

## 3. 生成探针：把上限放开，模型会补多长？

6 个“选中段落 → 真实意见”回合 × 3 个长度上限（40 / 80 / 160），每次 3 条 chip，
共 18 次调用，0 失败。

| 上限 | 平均 chip 字符 | 最长 chip | 超上限 | 平均 output tokens | 延迟 p50 / p95 |
|---:|---:|---:|---:|---:|---:|
| 40 | 14.2 | 25 | 0 | 35.2 | 1,065 / 1,243 ms |
| 80 | 20.0 | 36 | 0 | 45.5 | 1,134 / 1,280 ms |
| 160 | 28.3 | 56 | 0 | 57.3 | 1,186 / 1,374 ms |

- **模型不会填满上限**：即使允许 160 字符，平均也只有 28 字符、最长 56。
  它天然产出“一句完整短回复”，不是整条消息。
- 输出 token 从 35 到 57，差 22 tokens；按 $5/M 输出算，单次差 **$0.0001**，
  相对 ~976 input tokens 的费用可以忽略。**“补一句省成本”这个理由不成立。**
- 输入 token ~976（走网关，未预筛），延迟 ~1.1s p50、~1.3s p95，比检索任务略慢。
- 示例（T02 选中「forced commit 后端点不开 response」）：
  - cap 40：`对，forced commit 后端点不响应是根因`
  - cap 80：`对，forced commit 后端点不开 response 是直接原因`
  - cap 160：`对，A 是直接原因，先修 10 秒兜底`
  三条都是可发送的短回复，长的并没有变成整段。
- 与真实 draft 的字符 bigram Dice 只有 0.001–0.026：生成的是**替代回复**，不是用户原话的复述；
  Dice 不适合当质量指标，正式实验要用 same/near/different 人工/评判口径。

## 4. 回答“补一句还是补全文”

**成本不是决定因素，可用性才是。**

- 一句（~30-60 字符）与一小段（~80-120 字符）的输出差 ~20-60 tokens，
  单次差 ~$0.0001–0.0003；相对输入上下文可以忽略。
- 真实使用记录说：用户点的是**较完整的第一条**（81%），但它的中位长度只有 39 字符、
  上限 114 字符。**“补全文”没有证据支持；“补一句/一小段”有。**
- 生成探针说：模型在 160 上限下也只写 28 字符均值。要它写整条消息，得换一个明确的
  “写完整消息”指令与单独的交互，而不是把上限调大。

建议的 v1：

1. 每次 3 条，长度阶梯：第 1 条 **≤80 字符**（较完整，覆盖多个待答点），
   第 2、3 条 **≤40 字符**（更短的决定/确认）。上限 120 作为硬截断。
2. “展开成整条消息”作为**显式动作**（第二次调用），不放进默认批次；
   默认批次不该用整条消息去赌。
3. 对 quote 插入，“补”的单位是**选中的原文段落**（逐字），不是生成的句子；
   生成 chip 是“对这段的回复”，两者是不同动作。

## 5. “选中即生成建议”的实验设计

离线样本：509 个引用回合中的 60 个（30 near / 30 far；排除多引用回合）。
每个回合有：选中原文、来源消息、用户真实 draft（引用之外的文字）。

臂：

| 臂 | 条件 | 目的 |
|---|---|---|
| A 现状 | 首次 draw，不带 focus | 现有模型 chip 的下界 |
| B focus | 选中原文作为 focus | 选中锚点的增益 |
| C focus + 长度阶梯 | 第 1 条 ≤80，2/3 条 ≤40 | 推荐形态 |
| D focus + 160 | 上限放到 160 | 检验“更长是否更好” |

评价：

- 用 `reply-suggestions-bench` 的 same / near / different 口径（≥2 评判，保守一致度），
  对每个回合的真实 draft 判 3 条 chip；报告逐 chip 与逐消息命中率。
- 长度：平均/最大 chip 字符、超上限数。
- 成本/延迟：input/output tokens、p50/p95。
- 人工盲评 30 条：same/near/different + “会不会用它替代自己写”。
- 对照：quote chip 本身（逐字插入）不参与 same/near 评分，它解决的是另一个动作。

决策门：

- B 相对 A 的逐消息“同或近”至少 **+10 点**，否则选中锚点不值得自动触发；
- C 不劣于 B，且 chip 中位长度 ≤60；
- D 相对 C 没有 ≥10 点提升 → 不做“更长”；
- 延迟 p95 ≤1.5s；选中后 quote chip 必须立即出现，生成 chip 迟到不阻塞。

## 6. 限制

- 6 个回合 × 3 上限，只够验证协议与长度形态，不足以判质量。
- 真实使用记录混有缓存、重抽、多次点选；20/71 是“至少点选一次”的 draw 比例，
  不是逐次展示的点击率。
- 选中锚点的真实频率在 transcript 里不可见：只能看到最终引用了的 509 次；
  用户选中后不引用的次数未知。
- 生成 chip 与真实 draft 的 Dice 很低，说明真实意见更多是“针对这段的决定”，
  不是复述；正式实验必须用 same/near/different，而不是文本相似度。
