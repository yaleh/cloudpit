# E2 结果：简报可行性（B1 网关单次 vs B2 短 Claude Code 会话）

> 日期：2026-10-27 · 计划：`EXPERIMENT-PLAN.md` · 原始数据：`tmp/cockpit-briefing/`（`e2-b1-<n>.json`、`e2-b2-<n>.json`、`e2-summary.json`、`ledger.json`）· 图：`tmp/cockpit-redesign/e2-*.png`

## 1. 结论（先看这里）
- **B1（网关单次 + 宿主检查 ≤3 轮）8/8 通过**，p50 11.4 s、p90 16.2 s，平均约 1.3 万 token/条。
- **B2（`claude-fjdac -p` 短会话）6/8 通过**，p50 34.5 s、p90 37.5 s（最慢 58 s），平均约 14.7 万 token/条，是 B1 的约 11 倍。
- B2 的优势只有一个：**机械可核证据占比 62%（B1 25%）**，因为它真去读了 git / 文件。
- **过关线：B2 未过**（通过率不够，见 §6）。**建议产品化 B1**，B2 暂不上线；盲评还没做（图已备好，见 §7）。

## 2. 方法
- **事项**：从 `~/.cloudcli/auth.db`（只读）取当前「在问你」的会话 12 条；第 0 条是本实验的父会话，排除。抽样 8 条：1、2、3、4、5、7、9、11。每条上下文 = 转写尾部 + 观察层 digest（`e2-items.py`；会话 id 经 `sessions.jsonl_path` 映射到转写文件）。
- **B1**（`e2-b1.py`）：网关 `/v1/messages` 直连，模型 v4.1flash，关闭 thinking。提示词含 schema、radar 语义示例、骨架、一份完整示例。宿主用同一个 checker 检查（`e2-check.mjs`，先展开 `radarSemantic` 简写），失败就把错误回给模型，最多 3 轮。
- **B2**（`e2-b2.py`）：`claude-fjdac -p --output-format json --model v4.1flash --max-turns 8`。工具白名单 = Read / Grep / Glob、只写 `./brief.json`、`node brief-cli.mjs`、`git -C <repo> log|diff|show|status`。
  - 隔离：临时 `CLAUDE_CONFIG_DIR` + 仓库外的临时 cwd（`--add-dir` 指向仓库）。**与计划不同**：计划写 cwd 为主检出，为了不在本项目的转写目录里留文件改为仓库外。
  - 每次运行后核对：`~/.claude/projects/-data-home-yale-work-claudecodeui/` 无新增文件（8/8 为 0），模型 8/8 为 v4.1flash。
  - 宿主不信会话自称的结果，读 `brief.json` 重新检查。
- **密钥**：按 `gateway-probe.py` 的约定，只在子进程环境里传，没有打印、记录或落盘；网关主机已打码。
- **试点期间的迭代**（都计入 token）：
  1. B2 漫游到 max-turns、一次 check 都没跑 → 提示词内联 schema，并写明轮数预算。
  2. 用 heredoc 调 `check -` 被 Claude Code 的 bash 安全规则拦下 → 改为写 `./brief.json` 后再跑 `check brief.json`。
  3. 文档形状错误 → 给 B2 也加上骨架和示例，跟 B1 一致。
  4. `claude-fjdac` 偶发 exit 127 → 重试，最多 3 次、间隔 20 s。

**问错了问题（重要）**：第 3、11 条里，B2 的 headline 用的是 digest `askingYou` 里**更早一轮**的问题。
- 第 3 条：B2 问「要补 e2e 断言吗」，但这一步已经做完并提交了。
- 第 11 条：B2 问「A+C 还是只做 C」，但最新一轮问的是「你是哪种操作」。
- B1 两条都按转写尾部写对了（第 3 条：「是否推送 3b3d2a919」）。

由此看出两点：
- digest 的提问摘录可能落后于最新一轮，T1 决策摘要必须以**最后一条助手消息**为准。
- 简报提示词要写明「以最新助手消息为准，digest 只作参考」。

检查器发现不了这个问题，盲评时要特别看。

| token/条 | ~13.0k | ~147.2k |
| 机械证据占比 | 25% | 62% |
| `canvas` 使用 | 0 | 0 |

**失败规则直方图**（B1 统计每条第一次失败的规则；B2 统计最终失败原因）
- B1：`checklist-items`（每项必须带 `done`）×4；`unparseable-json` ×2（原始文本没留存，无法再细分）。
- B2：`unparseable-final-message` ×2（没有可用的 `brief.json`：1 次撞 max-turns，1 次自称完成但文件缺失或无效）。

几点观察：
- B1 的失败全部在第 2、3 轮修好，修复回路本身是有效的。
- `checklist.done` 必填是格式设计上的摩擦，不是模型的错：简报里的 checklist 是「确认前要检查的事」，本来就没有完成状态。建议改为可选、默认 false。这次没改，因为它是 schema 决策，不属于 checker 缺陷。
- `canvas` 两臂都没用过，计划 §1 问题 3 的答案目前是「不常用」，也没有出现值得升格为预置形式的 rationale。
- 雷达轴：除了必带的 rev/evid，每条都有 1–4 条按事项自定的轴（如「误杀风险」「按住期间稳定」），读起来贴题。

## 8. 建议
1. **产品化 B1**：满足 3 分钟门槛的提问一到就预生成。提示词带 schema、骨架、示例；宿主检查，最多 3 轮；不过就显示默认卡。提示词里加一条「以最新助手消息为准」。
2. **B2 暂不上线**。以后如果给需要现场取证的重事项用：`--max-turns` 取 10，沿用基于文件的 check 和骨架加示例，单条预算约 15–18 万 token。
3. **每日预算**：按每天约 24 个提问粗估。
   - B1 每天约 0.31M token；日上限 **0.5M**，单条上限 **30k**。
   - 如果启用 B2：每天最多 **5 条**（约 0.8M）。
4. **格式改动**：`checklist.done` 改为可选；B1 把原始输出存下来，`unparseable-json` 才能分析。
5. **digest 的提问摘录要跟着最新一轮刷新**（见 §4）。
